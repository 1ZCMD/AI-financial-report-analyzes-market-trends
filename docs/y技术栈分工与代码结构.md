## 1. 项目目标与总体流程

### 1.1 项目目标

对已采集的期货分析师日评、策略报告等材料进行读取、解析、清洗和观点提取，将结果结构化入库，并通过网页图表展示一段时间内各期货品种的机构预测情况。

项目定位是**期货研报观点提取与市场预期可视化系统**，不是期货价格预测模型，也不是自动交易系统。

### 1.2 业务处理流程

```text
企业数据库 / 文件目录中的研报
              |
              v
       文件读取与去重
              |
              v
    PDF / HTML / 图片内容解析
              |
              v
       正文与表格清洗
              |
              v
       判断观点是否明确
          /          \
         /            \
        v              v
   规则直接提取      大模型辅助判断
         \            /
          \          /
           v        v
        统一结构化观点
              |
              v
       数据校验与去重
              |
              v
           MySQL
              |
              v
     指标计算与历史数据查询
              |
              v
       FastAPI 提供接口
              |
              v
       Vue + ECharts 看板
```

### 1.3 两类观点提取路径

企业任务书明确区分两类情况：

1.  文章中已有明确品种趋势预测：直接提取预测结果并入库。
2.  文章中没有明确品种趋势预测：将相关描述交给大语言模型分析，再将判断结果入库。

因此，建议采用"**规则提取优先，AI
分析补充**"的方式。明确的表格、标题或标准字段优先使用规则提取；需要结合上下文判断的观点再调用
AI。两条路径最终输出同一种结构化数据格式。

## 3. 系统架构与模块边界

建议采用**前后端分离的单体后端架构**。批量研报处理通过 Python
脚本或任务模块运行；网页访问时，FastAPI
读取已经入库的数据，不在用户打开页面时临时批量调用 AI。

### 3.1 模块职责

模块 主要职责 不负责的内容

## 5. 数据结构与接口约定

### 5.1 统一观点 JSON（建议）

以下为基于宝城期货样本整理的**建议数据格式**，不是企业已经提供的固定接口格式。A、B、C
应在开发第一天确认最终字段名和字段类型。

```json
{
  "institution": "宝城期货",
  "report_date": "2024-03-01",
  "variety_code": "CU",
  "contract_code": "CU2404",
  "horizon": "intraday",
  "direction": "BULL",
  "raw_direction": "震荡偏强",
  "strategy": "逢低做多",
  "reason": "伦铜超跌反弹",
  "evidence": "日内观点：震荡偏强",
  "source_page": 1,
  "extraction_method": "RULE",
  "confidence": null
}
```

字段说明：

字段 含义

---

institution 机构名称
report_date 研报发布日期
variety_code 标准化品种代码，例如 CU
contract_code 具体合约，例如 CU2404
horizon 预测周期，例如 intraday / short / medium
direction 标准方向：BULL / BEAR / NEUTRAL / UNKNOWN
raw_direction 研报原始表述
strategy 策略参考，单独保存
reason 观点理由摘要
evidence 支持该观点的原文
source_page 原文所在页码
extraction_method RULE 或 AI
confidence AI 置信度；规则提取可为空

一份研报可以包含多个品种、多个预测周期，因此输出应允许包含多条观点记录，而不是强制每份研报只对应一条观点。

### 5.2 方向标准化建议

原始表述示例 标准方向

---

上涨、偏强、震荡偏强 BULL
下跌、偏弱、震荡偏弱 BEAR
震荡、区间震荡 NEUTRAL
未明确判断、无法判断 UNKNOWN

以上是项目内部建议的归一化口径，最终映射需要全组确认。UNKNOWN
不应当计入看平。

预测周期建议至少保留日内、短期、中期。宝城期货样本说明短期为一周以内，中期为两周至一月。不同周期应分开统计，不能混在同一个指数中。

### 5.3 数据库核心实体建议

组长方案提到数据库建表脚本和 6 张表、1 个视图，但当前材料没有附上完整
SQL。因此以下是建议的逻辑实体，实际表名、字段和索引需要与现有建表脚本核对：

实体 作用

---

institutions 机构信息
varieties 期货品种信息
reports 原始研报元数据、日期、来源路径、文件哈希
opinions 一份研报中提取出的多条品种观点
daily_sentiment 每日、品种、预测周期的统计快照
processing_logs 解析、AI 抽取、入库等处理状态和错误信息

如企业已有数据库结构，应优先适配企业现有结构，不要未经确认直接修改生产库。

### 5.4 API 接口

组长原方案的五个主要只读接口如下：

接口 功能

---

`GET /overview` 获取指定品种的当日概览、KPI 和指数

前端 D 只依赖接口文档和 Mock 数据开发；后端 C 保证真实接口字段与 Mock
字段一致。

## 6. 指标计算口径

组长方案给出的一致性预期指数公式为：

\[ I = `\frac{B-S}{B+S+N}`{=tex}`\times100`{=tex} \]

其中：

- B：看多机构数
- S：看空机构数
- N：看平机构数

建议保留原方案公式，但在开发前确认以下统计口径：

1.  同一家机构同一品种、同一预测周期、同一统计日期重复发布多份研报时，如何去重。
2.  日内、短期、中期观点必须分开统计。
3.  UNKNOWN、抽取失败、低置信度观点不应自动当作看平。
4.  分母为零时返回 `null`，不能误报为指数 0。
5.  展示指数时同时展示有效覆盖机构数，避免少量样本造成误读。
6.  历史快照重算应保持幂等，重复执行不产生重复数据。

置信度阈值、同机构多份研报取最新还是按其他规则处理，需要通过人工标注样本和企业业务口径确认。

## 12. 开发前需要向企业或组长确认的问题

1.  研报原始数据究竟从企业数据库读取，还是从指定文件目录读取？是否两者都有？
2.  企业数据库类型、表结构、连接权限和数据读取方式是什么？
3.  PNG 图片是否属于第一版必须支持的输入格式？是否要求 OCR？
4.  企业 AI 接口的调用地址、鉴权、SSE 格式、并发限制和调用额度是什么？
5.  企业是否已有六张表和一个视图的建表 SQL？是否要求沿用？
6.  原文溯源需要打开本地文件、企业文件系统链接，还是数据库中的原文地址？
7.  第一版最终验收的数据日期、品种范围和研报数量是多少？
8.  前端 Vue 版本、部署环境和浏览器是否有企业指定要求？

**在这些问题确认之前，不应把建议方案中的数据库字段、AI
参数、数据量和部署方式当成企业已经确定的要求。**

## 13. 最终开发原则

1.  先统一数据格式，再并行开发。
2.  先跑通少量真实数据，再扩大批处理规模。
3.  明确观点直接提取，模糊观点再交给 AI。
4.  每条观点尽量保留原始表述、原文证据和来源页码。
5.  指标口径必须统一，尤其是预测周期和机构去重。
6.  前端先用 Mock 开发，后端接口完成后再联调。
7.  以可运行、可追溯、可测试、可演示作为第一版目标。
